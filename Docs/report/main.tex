\markright{Abstract}
\begin{center}
{\bfseries\large ABSTRACT}
\end{center}
\vspace{0.25cm}
AI-Powered Smart Farming is a software platform designed to help farmers inspect crop-leaf images, identify the likely crop and disease condition, estimate visible severity, detect selected pest classes, and receive contextual agronomic guidance. The project combines a web API, an AI inference service, a relational data layer, object storage, multilingual translation, speech narration, farm and plot records, weather context, and a role-based workflow for expert review. The platform targets five crop categories in its crop-identification stage: Cotton, Groundnut, Pepper Bell, Potato, and Tomato.

The documented vision stack uses EfficientNet-B0 for five-way crop identification, crop-specific EfficientNet-B2 disease classifiers, a YOLOv8-nano classification model for selected pest categories, and image-quality, leaf-region, severity, and confidence checks. Agronomic guidance is primarily grounded in an ICAR/KVK-oriented knowledge base, with a documented provider fallback chain and structured, validated output. Qwen3-4B is an experimental advisory path and is not represented as the primary deployed chain. The platform separates a React/Vite web client, a FastAPI backend, and a unified Hugging Face Spaces AI service; Supabase provides PostgreSQL and private object storage, while Upstash supports caching and scheduled/background workflows. Authentication is documented around JWTs, refresh-token cookies, Argon2id password hashing, and farmer, expert, and administrator roles.

The report distinguishes documented implementation from experimental paths and planned improvements. The current Model Cards report 99.53\% held-out test accuracy and 99.45\% test macro-F1 for crop identification, with lower reported accuracy on uncontrolled field images than on controlled images. These are documentation-reported measurements, not a fresh independent rerun, and do not guarantee performance on arbitrary farm imagery. The report also records model-card inconsistencies and MLOps promotion requirements that should be resolved before treating the metrics as publication-grade evidence \cite{model_cards}.

\vspace{0.20cm}

\chapter{Introduction}
\section{Background}
Agriculture is affected by crop disease, pests, changing weather, nutrient deficiencies, and differences between controlled and field conditions. Timely recognition of visible symptoms can help a farmer decide whether to inspect a crop more closely, seek expert advice, or take a suitable next step. Manual diagnosis remains valuable, but it may be limited by access to experts, language barriers, and the time required to inspect many plants.

Computer vision can classify visual patterns in crop images, while a backend platform can connect those predictions to farmer history, plot information, weather observations, and structured recommendations. A practical system must do more than return a class label: it should validate the uploaded image, communicate uncertainty, preserve the history of decisions, protect user data, and support correction when an automated result is questionable.

\section{Project overview}
The AI-Powered Smart Farming project is an end-to-end software platform for crop-leaf diagnosis and agricultural decision support. Its documented crop identifier covers Cotton, Groundnut, Pepper Bell, Potato, and Tomato. Crop-specific disease classifiers follow crop identification, while the later pipeline stages estimate severity, classify selected pests, retrieve contextual information, and generate a structured advisory. The user-facing product includes farmer workflows and administrative/expert workflows.

\section{Problem statement}
Farmers need a practical way to submit a crop image and receive an understandable, language-appropriate diagnostic result. A useful platform must handle poor-quality images, distinguish between supported and unsupported classes, provide transparent confidence information, and escalate uncertain cases rather than treating every model prediction as certain. It must also provide secure account management, prediction history, feedback, expert review, and a controlled mechanism for updating models as better-labelled data becomes available.

\section{Objectives}
\begin{enumerate}
  \item Identify the crop represented in a submitted leaf image.
  \item Route the image to the appropriate crop-specific disease classifier.
  \item Apply image-quality validation and leaf-region processing before classification.
  \item Estimate visible affected area and map it to a severity bucket.
  \item Classify selected pest categories when the pest stage is enabled.
  \item Return structured actions, treatment guidance, prevention, and monitoring advice.
  \item Present results in the user's preferred language and support speech narration.
  \item Maintain prediction history, farm/plot context, feedback, and expert-review workflows.
  \item Support dataset export, evaluation, model registration, and controlled model promotion.
  \item Operate within low-cost/free-tier hosting constraints while keeping a path to dedicated infrastructure.
\end{enumerate}

\section{Scope and boundaries}
The documented implementation is an image-based decision-support platform. It is not a substitute for a qualified agronomist, laboratory diagnosis, or local pesticide-label guidance. The system only supports its configured crop and disease classes. It should not claim a definitive diagnosis for an unknown crop, an image outside the training distribution, or a low-confidence result. Weather and farm-context features improve context but do not, by themselves, prove the cause of a plant symptom.

\noindent\textbf{Report organisation.} Chapter 2 presents the motivation and requirements; Chapter 3 describes the system architecture; Chapters 4 and 5 discuss dataset design and the AI inference pipeline. Chapters 6--10 cover the backend API, security, MLOps, testing and evaluation, and deployment. Chapters 11--13 present the discussion and limitations, future scope, and conclusion.

\chapter{Existing System, Motivation and Requirements}
\section{Motivation}
A useful agricultural AI application must bridge several distinct tasks: vision inference, agronomic interpretation, regional-language communication, and ongoing record management. A standalone image classifier solves only part of the problem. Smart Farming connects prediction outputs with farm and plot records, historical scans, weather context, multilingual content, and human review.

\section{Existing workflow challenges}
Common challenges in a manual or fragmented workflow include delayed access to expert guidance, inconsistent descriptions of symptoms, difficulty comparing the same plant over time, and limited traceability of the recommendation that was shown to a farmer. A computer-vision model can also fail when a field image differs from its training data. The project therefore includes image validation, confidence-aware review, historical records, and a route for experts to correct or override a result.

\section{Application layers}
\textbf{Client layer:} The React/Vite web application and Flutter mobile client provide user interaction. Farmer workflows focus on submitting scans, understanding results, viewing history, and managing farm context. Administrative and expert screens support review, configuration, and model operations.

\textbf{API gateway:} The FastAPI service is the central contract boundary. It validates incoming requests, verifies the user's identity and role, orchestrates the prediction pipeline, persists results, and issues signed media URLs. The API is documented for deployment on Render.

\textbf{AI inference layer:} The unified AI service is documented as a Hugging Face Space named \texttt{Maharsh8805/smart-farming-ai}. It exposes model-backed operations for vision and related AI services. The exact resource limits and cold-start behaviour depend on the Space hardware and plan.

\textbf{Data layer:} Supabase PostgreSQL stores application entities and structured prediction records. Supabase Object Storage stores original and processed media. Upstash Redis REST is used for selected cache keys. An ARQ worker and queue are used in the optional asynchronous mode.

\section{Synchronous and asynchronous modes}
The API documentation describes two execution modes. With \texttt{REQUIRE\_REDIS=False}, the prediction request runs synchronously and returns the completed result. With \texttt{REQUIRE\_REDIS=True}, the API enqueues work and returns a placeholder; clients follow progress through a WebSocket and can query the result. The synchronous path is simpler for a low-traffic deployment but can be vulnerable to request timeouts when inference is slow. The queue path improves separation between request handling and long-running work but adds worker, Redis, and operational complexity.

The index-to-label order used by a trained checkpoint must come from its matching label map, not from this illustrative table. Training and inference must use the same mapping.

\section{Environment variation}
The dataset distinguishes controlled-environment images from uncontrolled or field-captured images. This distinction matters because background clutter, lighting, leaf orientation, multiple leaves, and camera quality can alter the visual distribution. A high score on controlled images alone would not establish field readiness. The newer Model Cards report 99.65\% crop-identification accuracy on the controlled subset and 99.35\% on the uncontrolled field subset. The older notebook summary contains different environment figures; this report uses the newer Model Cards and treats the values as project-reported rather than independently verified results \cite{model_cards,dataset_doc}.

\section{Folder-label normalisation}
The supplied folder-renaming document maps original directory names to shorter codes \cite{dataset_doc}. These codes are useful for file organisation, but they should not become user-facing diagnosis labels. Label normalisation should preserve the original source label and the canonical label in metadata so that data lineage is recoverable. For merged sources, the data manifest should record source dataset, source URL or identifier, original class, canonical class, environment, split, and any expert correction.

\section{Data quality and governance}
A reliable training dataset needs checks for corrupt files, exact duplicates, near-duplicates, label conflicts, class imbalance, and distribution leakage. Multiple photos of the same plant or plot should not be randomly scattered across training and test splits if the objective is to estimate performance on unseen plants or plots. The MLOps guide describes deterministic grouping by \texttt{plot\_id} to reduce rescan leakage, a replay-buffer mixing strategy, and use of verified dataset candidates; these controls should be checked against the actual export implementation and metadata \cite{mlops_guide}.

\section{Recommended split policy}
The documented training export example uses 70\% training, 15\% validation, and 15\% test data. The test set should be held out from checkpoint selection and threshold tuning. When data is grouped by plot or plant, group-aware splitting is preferable to simple image-level random splitting. The export should include a manifest and timestamp so that each model result can be linked to the exact data version.

\section{Image validation and preprocessing}
The API documentation describes a maximum image size of 10 MB and accepts JPEG, PNG, or WebP. A magic-byte/image decoding check is performed before saving. Duplicate submissions are checked through a content hash. The documented quality checks include blur, luminance, and leaf-region detection. One reference gives a Laplacian-variance blur threshold above 50 and luminance bounds of 40--240; project configuration may contain different values, so a single canonical configuration must be confirmed before production \cite{api_spec}. Validation errors should explain how the farmer can improve the image without exposing implementation details.

\section{Crop identification}
The crop identifier is EfficientNet-B0 with five outputs and 224 $\times$ 224 RGB input \cite{efficientnet,pytorch_docs}. The newer Model Cards report 99.53\% held-out test accuracy (4,240/4,260), 99.45\% test macro-F1, and 99.50\% weighted F1. Per-class recall is reported as 98.6\% for Cotton, 99.7\% for Groundnut, 99.5\% for Pepper Bell, 100.0\% for Potato, and 99.2\% for Tomato. The same card reports 99.65\% accuracy on the controlled set and 99.35\% on the uncontrolled field set. Temperature scaling with $T=1.08$ is documented; expected calibration error is reported as falling from 0.0210 to 0.0072, with Brier score 0.0076. These are values transcribed from the supplied Model Cards, not independently rerun measurements. The report does not infer statistical independence or absence of leakage beyond what the data-preparation documentation establishes \cite{model_cards,dataset_doc}.

\section{Crop-specific disease classifiers}
After crop identification, the Decision Engine routes the image to the model associated with the predicted crop. The Model Cards document crop-specific disease classifiers, with EfficientNet-B2 as the disease-classifier architecture \cite{model_cards}. Each model needs a matching checkpoint and label mapping. Model selection must fail safely if the configured checkpoint is missing, labels do not match the output dimension, or the crop label is unsupported. The service should not silently use a model for a different crop.

\section{Severity analysis}
The project documents a visual affected-area estimate and severity bucket. A previous implementation description specifies a mask-based HSV heuristic and buckets Mild below 20\%, Moderate from 20\% to 50\%, and Severe above 50\%. This should be treated as a heuristic for visible symptom coverage rather than a calibrated measure of biological damage or yield loss. It can be affected by leaf colour, lighting, background segmentation, and the symptom morphology. The final implementation should have one authoritative set of thresholds and should test boundary values explicitly.

\section{Pest classification}
The documented pest stage uses a YOLOv8-nano classification model, rather than assuming that it produces bounding boxes \cite{model_cards,ultralytics_docs}. A previous project note lists four pest classes: Aphid, Army Worm, Leaf Miner, and Spider Mite; Thrips was excluded due to insufficient training data. The actual supported class list should be read from the deployed model's labels or model card at runtime. The API should return pest labels and confidence values only when this stage completes successfully; an unavailable pest stage should be distinguishable from a confident prediction of no pests.

\section{Advisory generation}
The documented AI-service advisory chain uses the local \texttt{advisory\_kb.json} v2 knowledge base (56 condition entries and 155 aliases across five crops and pest/fallback categories), followed by Groq Llama-3.3-70B, Google Gemini 2.5 Flash, and a local Qwen2.5-1.5B-Instruct fallback. The backend also documents a separate Qwen3-4B-Instruct path through Hugging Face inference with TF-IDF retrieval; this is treated here as experimental/parallel rather than conflated with the primary AI-service chain. The four-field output is immediate action, treatment, prevention, and monitoring, with schema validation and a standard disclaimer. Knowledge-base entries and safety retrieval should remain authoritative for high-risk treatment details. The report does not claim that every model-provider fallback is available on every deployment or that every recommendation has undergone field validation \cite{model_cards}.

\section{Confidence and expert escalation}
Confidence scores should not be presented as universal probabilities unless calibrated. A threshold-based escalation policy can route uncertain results to expert review, but thresholds must be chosen using validation data and measured against the cost of false negatives and false positives. The project includes an expert-review workflow for farmers to request review and for experts to approve, override, or request a rescan. The UI should clearly distinguish model output from expert-verified output.

\section{Expert review}
A farmer may explicitly request a review. The documented review transitions begin at \texttt{pending}; an expert can approve or override to \texttt{verified}, or request a rescan to \texttt{rescan\_requested}. A decision against a review that is already verified should be rejected with a conflict response. The expert may flag a case for a future retraining dataset, but this flag must not be confused with automatic inclusion in training: eligibility, consent, quality, label validation, and export policy still apply.

\section{Frontend and mobile responsibilities}
The web and mobile clients should share the same API contract and role semantics. The farmer interface should prioritise image capture/upload, clear validation feedback, result interpretation, next actions, history, plot selection, and language/audio controls. Expert review is a separate privileged workflow. Admin functions such as model promotion and database maintenance should not be exposed to farmer accounts. Mobile screens should work under intermittent connectivity and should avoid storing long-lived credentials in insecure plaintext storage.

\chapter{Security, Privacy and Access Control}
\section{Authentication}
The authentication reference documents JWT bearer access tokens with a 30-minute lifetime and refresh tokens with a 30-day lifetime stored in an HttpOnly cookie. Refresh calls rotate the token pair. Passwords are hashed with Argon2id using the parameters stated in the security reference. The server is intended to refuse production startup when a default JWT secret is configured; the development-only bypass must never be available in production \cite{auth_reference}.

\section{Media access}
Original images, processed images, masks, and narration audio may contain private information. The documented policy limits farmers to their own predictions, experts to cases associated with their review queue, and administrators to platform-wide access. Short-lived signed URLs reduce the risk of persistent public links. Access checks must occur before issuing a signed URL; hiding a URL in the frontend is not an access-control mechanism.

\section{Role-change guards}
Two safeguards are documented for administrator role changes: an administrator cannot demote their own account, and the last remaining administrator cannot be demoted. These checks protect against accidental lockout. Role changes should be audited with actor ID, target ID, old role, new role, timestamp, and reason.

\section{Privacy and retention}
The system should minimise personal data in logs, restrict access to images, and define retention and deletion policies for original uploads, generated media, and prediction metadata. Data exported for retraining should be limited to eligible records and should carry provenance. User images should not be included in training merely because they exist in storage. Where appropriate, the system should provide a documented deletion or de-identification path.

\section{Security review checklist}
\begin{itemize}
\item Verify that production has a strong, rotated JWT secret and \texttt{DEBUG=False}.
\item Ensure the development \texttt{X-User-ID} bypass is disabled in production.
\item Confirm cookie flags, CORS allowlists, rate limits, and trusted proxy configuration.
\item Test object-level authorisation for predictions, media, farm plots, feedback, and review records.
\item Ensure signed URLs expire and cannot be issued to unauthorised users.
\item Validate uploaded file content rather than trusting filename extensions or client MIME type.
\item Avoid logging access tokens, passwords, reset tokens, signed URLs, or full sensitive payloads.
\item Audit admin actions and model promotions.
\end{itemize}

\section{Two-phase training}
The documented training strategy first freezes the feature extractor and trains the classifier head during warmup. It then unfreezes the backbone for fine-tuning, using a lower learning rate for the backbone than for the head and a cosine learning-rate schedule. This approach can stabilise early learning and reduce abrupt changes to pretrained representations. Its effectiveness should still be measured for each dataset and architecture.

\section{Evaluation artefacts}
Each run should retain the best checkpoint, latest checkpoint, label mapping, metrics, training configuration, dataset export manifest, and logs. Metrics should include validation and test results, per-class precision/recall/F1, confusion matrix, epoch history, and the number of epochs actually trained. A checkpoint should not be promoted based only on training accuracy or a single aggregate score.

\section{Dataset export}
The updated guide describes an admin-protected dataset export endpoint, a 70/15/15 split, preprocessed image targets, and metadata containing provenance. It also describes deterministic grouping by plot to reduce leakage and a replay-buffer mixing policy. The export API, filters, and exact response format should be tested against the deployed version. The documentation's use of \texttt{added\_to\_dataset} as the default eligibility marker should be enforced server-side rather than trusted from client input \cite{mlops_guide}.

\section{Model promotion}
The model registry workflow records a model key, version, checkpoint path, labels path, validation and test metrics, and notes. Promotion is documented to update the configuration and registry atomically. In synchronous production mode, the guide notes that a Redis hot-reload event is not published; therefore, the updated model artefacts must also be deployed to the AI microservice. A successful registry update does not prove that the live inference service is using the new weights.

\section{Metric interpretation}
Accuracy is the fraction of correct predictions. Precision measures how many predictions assigned to a class are correct; recall measures how many true examples of that class are found; F1 is the harmonic mean of precision and recall. Macro-F1 computes F1 per class and averages the class scores equally, making it more sensitive to weak minority classes than overall accuracy. Confidence calibration should be assessed separately, because a model can be accurate while overconfident.

\section{Important test cases}
\begin{enumerate}
\item Upload a valid image for each supported crop and verify the correct model route.
\item Upload an unsupported crop and confirm the system does not force a misleading supported label.
\item Upload a corrupt image, oversized image, wrong MIME payload, blurred image, and poorly exposed image.
\item Repeat the same image upload and verify deduplication behaviour and user-facing feedback.
\item Test confidence thresholds just below, at, and above each configured boundary.
\item Verify that label-map length equals the model output dimension.
\item Simulate an unavailable AI service and ensure the API returns a controlled error rather than a partial success.
\item Verify translations preserve treatment details, units, cautions, and negation.
\item Verify that farmer A cannot access farmer B's prediction, image, audio, or plot.
\item Verify that an expert cannot access media for cases outside the permitted review scope.
\item Attempt to demote the current administrator and the last remaining administrator.
\item Evaluate a promoted checkpoint against a known regression set and verify rollback.
\end{enumerate}

\section{Limitations of the reported evaluation}
The available summary does not provide full disease-classifier metrics, pest-classifier confusion matrices, advisory correctness rates, calibration plots, or latency distributions for the currently deployed service. Those values should not be invented. They should be measured and added after a reproducible test run with a recorded dataset version and model hashes.

\chapter{Deployment and Cost-Conscious Operations}
\section{Documented deployment}
The latest documented deployment uses Vercel for the React/Vite web SPA, Render for the FastAPI backend, and the unified AI service at the Hugging Face Space \texttt{Maharsh8805/smart-farming-ai} (port 7860). Supabase supplies PostgreSQL and private object storage; media access uses short-lived signed URLs (documented as 15 minutes). Upstash Redis REST supports selected cache keys and QStash schedules weather-risk and maintenance jobs. GitHub Actions workflows are documented for AI Space deployment and database migrations. A Docker Compose self-hosting target is also documented, but it is a deployment alternative, not the selected hosted topology. Scheduled keepalive jobs can reduce cold starts but do not guarantee uptime or bypass provider quotas \cite{project_readme,changelog,hf_spaces,supabase_docs}.

\section{Free-tier constraints}
Free-tier deployments are useful for prototypes and low-volume pilots, but they have resource and reliability limits. CPU-only inference can increase latency, hosted spaces may sleep or cold-start, persistent storage may be limited, and third-party quotas or pricing can change. The system should be designed so that the API can return a controlled unavailable/timeout response when the inference service is cold or unreachable. A keepalive ping should not be treated as a guarantee of uptime or as a replacement for a production service-level agreement.

\section{Operational recommendations}
\begin{itemize}
\item Keep the API gateway lightweight; avoid loading large ML weights into the same constrained process.
\item Load each model once per worker where memory permits and cache deterministic low-risk responses only when safe.
\item Set explicit connect/read timeouts and bounded retries for external inference calls.
\item Use request IDs and structured logs to correlate API, AI service, database, and storage events.
\item Track p50/p95 latency, error rate, cold-start duration, memory, model version, and inference-stage failures.
\item Pin dependency versions and run a build/smoke test before deployment.
\item Maintain a known-good model artefact and a rollback procedure.
\item Document service quotas and review them before any public demonstration or pilot.
\end{itemize}

\section{Suggested deployment smoke test}
After deployment, verify the health endpoint, model loading, label-map integrity, a known-good image prediction, a bad-image rejection, language translation, TTS generation, storage upload/read, authenticated prediction retrieval, and a role-protected admin route. The smoke test should be automated in CI where possible and should avoid using real farmer data.

\chapter{Results, Discussion and Limitations}
\section{Implementation status and evidence boundaries}
The README, changelog, and implementation summary describe the Render--Hugging Face Spaces--Vercel--Supabase--Upstash deployment as the current documented hosted architecture. The vision pipeline, role-based application flows, private media access, expert-review workflow, and MLOps dataset-export interface are documented as implemented components. The primary advisory path described by the AI-service Model Cards is the ICAR/KVK knowledge base with provider fallbacks; Qwen3-4B is retained as an experimental/parallel backend path. In contrast, a fully automated closed-loop retraining-and-promotion process is not claimed as complete: the MLOps guide specifies export, training, evaluation, safety gates, registry updates, and redeployment steps, and the live service must be verified after new weights are promoted. Features listed in the future-scope section remain proposed improvements rather than delivered capabilities. The source references disagree in some details, including model class tables, threshold conventions, and route status; this report does not silently resolve those discrepancies \cite{project_readme,changelog,model_cards,mlops_guide}.

\section{Current strengths}
The documented design has several sound architectural properties: the API and inference service are separated; crop-specific disease models can be updated independently; the pipeline exposes stage statuses; the backend supports history and expert review; media access is scoped by role; and the MLOps guide describes reproducible exports and model promotion. The use of structured advisory fields is preferable to returning an unconstrained paragraph alone, because it gives the frontend predictable sections to render.

\section{Areas requiring verification}
The project documents contain details from different revision dates. Thresholds, route names, runtime versions, mobile token storage, and deployment URLs should be reconciled against the current source code and deployed OpenAPI schema. In particular, the API reference documents a blur threshold of Laplacian variance greater than 50, while other project configuration notes may use a different threshold. A single authoritative configuration should be adopted and the documentation generated from it where possible.

\section{Model and data limitations}
High performance on a curated dataset may not transfer to images from different phones, regions, crop varieties, growth stages, or weather conditions. Disease classes can overlap visually; nutrient deficiency, pest damage, and infectious disease may co-occur. Image-level classification cannot necessarily localise symptoms or establish causality. The severity heuristic estimates visible affected area, not agronomic loss. Pest classification is limited to its trained categories and should not be described as comprehensive pest detection.

\section{Advisory limitations}
A language model can produce plausible but unsupported treatment instructions. The knowledge base, rule engine, and safety validator should define approved treatment options, contraindications, label-rate constraints, and escalation rules. Each advisory should be traceable to a source and revision. When the knowledge base has no safe matching entry, the system should say that it cannot confidently recommend a treatment and should refer the farmer to a qualified local expert.

\section{Operational limitations}
A multi-service architecture adds network dependencies and failure modes. Free-tier services can sleep, rate-limit requests, or change resource allowances. CPU-only models may be slow under concurrent load. Synchronous requests may exceed gateway timeouts; asynchronous mode introduces queue and worker dependencies. Production readiness requires observability, alerting, backup/restore tests, and a documented recovery process.

\chapter{Future Scope}
\section{Explainable AI}
A future explanation panel could show the predicted class, confidence, relevant visual region, and reasons for escalation. Visual attribution maps should be treated as model-debugging aids rather than proof that the model used a medically or agronomically valid cue. Explanations should be evaluated with domain experts.

\section{Multi-plot and longitudinal analysis}
Linking scans to a plot enables comparison across dates and supports follow-up workflows. Future versions can show whether symptoms appear to increase or decrease, provided images are captured consistently enough for comparison. A trend line should not imply precise disease progression when lighting, angle, or plant identity changes.

\section{Offline-first and regional-language access}
A mobile workflow can cache non-sensitive reference content, allow users to prepare a scan offline, and upload it when connectivity returns. Regional-language prompts and text-to-speech can improve accessibility. The interface should make it clear when a result is generated locally, retrieved from cache, or produced by a cloud model.

\section{Weather-triggered risk alerts}
Weather may be used to raise a risk signal when conditions are conducive to a known disease, but it should not be presented as diagnosis. Alerts should disclose their inputs, geographic resolution, time window, and uncertainty. They should be evaluated for alert fatigue and false alarms.

\section{Human-in-the-loop improvement}
Expert overrides and verified farmer feedback can create a useful improvement loop. Before using those cases for retraining, the pipeline must check consent, image quality, label consistency, duplication, class balance, and split leakage. Model releases should be versioned and compared with the previous production model.

\chapter{Conclusion}
The AI-Powered Smart Farming project combines crop identification, disease classification, severity estimation, pest classification, advisory generation, localisation, farm context, and expert review into one documented platform. Its architecture separates the API gateway from the AI inference service and provides role-scoped access to user records and media. The MLOps workflow aims to turn verified corrections into reproducible dataset exports, evaluated checkpoints, and controlled deployments.

The project-reported crop-identification metrics are promising for the evaluated dataset, but they do not remove the need for field-domain testing, calibration, and safe rejection of uncertain inputs. The highest-value next steps are to reconcile implementation and documentation, establish a rigorous field test set, enforce advisory provenance and safety rules, test object-level authorisation, and make deployment health observable. These improvements would strengthen trustworthiness without requiring an immediate move away from free-tier services.

\chapter{Reproducibility Checklist}
\begin{itemize}
\item Record the Git commit hash and date used to build the report.
\item Record the exact dataset export ID, timestamp, and manifest hash.
\item Record checkpoint hashes, model names, label-map hashes, and preprocessing version.
\item Record the deployed API URL and AI service revision; remove secrets from all screenshots.
\item Run unit, API, authorisation, integration, and end-to-end tests.
\item Attach actual model metrics rather than copying illustrative values.
\item Confirm all endpoint paths against the deployed OpenAPI schema.
\item Compile the LaTeX file and check references, figures, and table overflow.
\end{itemize}
